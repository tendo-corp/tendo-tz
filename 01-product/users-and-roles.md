# Пользователи и роли

Кто работает в системе, что видит и что может делать каждая роль: описание ролей и их стартовых экранов, устройство доступа (роль → матрица прав → гранты на объекты), права по умолчанию, сводная матрица «роль × действие» по всем доменам, доступ к адресам интерфейса и расхождения, которые нужно устранить при воссоздании.

Связанные разделы: требования к авторизации — [../07-architecture/security.md §2](../07-architecture/security.md#2-авторизация); вход, сессии, матрица прав — [../02-business-logic/identity.md](../02-business-logic/identity.md); гранты на объекты — [../02-business-logic/portfolios.md](../02-business-logic/portfolios.md); права по тендерам подробно — [../02-business-logic/tenders.md §5](../02-business-logic/tenders.md#5-права-роль--действие); глоссарий — [glossary.md](glossary.md); экраны каркаса и гейта — [../03-screens/shell.md](../03-screens/shell.md).

Подписи ролей в интерфейсе: «Администратор», «Тендерный специалист», «Служба безопасности», «Юрист», «Контрагент», «Лид», «Владелец площадки». Роль с неизвестным интерфейсу кодом получает экран «Для вашей роли здесь нет рабочего места» с кнопкой «Выйти».

Одна учётная запись — одна роль. Пользователь контрагента принадлежит ровно одной организации; у организации может быть сколько угодно пользователей.

## 2. Как устроен доступ

Доступ решает **сервер** на каждом запросе; интерфейс лишь прячет недоступное. Слои проверки:

| Слой | Что решает | Где настраивается |
|---|---|---|
| 1. Контур роли | Сотрудник (`admin`, `tender_specialist`, `security`, `lawyer`) / пользователь контрагента / лид / владелец площадки. Пользователь контрагента ходит только в `/me/*`, свои тендеры и чаты; лид — никуда; владелец — только `/auth/*` и `/owner*` | Зашито в код |
| 2. Матрица «роль × действие» | 14 кодов прав (`portfolios.manage`, `tenders.manage`, …) у ролей-сотрудников; администратор обходит матрицу | **Настраивается** администратором: «Настройки → Пользователи и роли → Права ролей»; строки «Администратор», «Контрагент», «Владелец площадки» заблокированы |
| 3. Гранты на дерево объектов | Какие портфели/объекты (с подобъектами) видит сотрудник; администратор — все | Настраивается на пользователя: карточка пользователя → «Доступ к объектам» |
| 4. Персональный флаг «видит финансы» | Видеть цены, суммы, протокол, ИИ-анализ; складывается по ИЛИ с правом `finance.view` | Карточка пользователя; администратору — всегда |
| 5. Повторный ввод пароля | Необратимые действия: закрытие тендера, перевыпуск/отзыв ссылки участника, сброс чужой MFA | Зашито в код |
| 6. Ролевые проверки внутри действий | Оси проверки контрагента, решение по квалификации, пул и опыт работ контрагента, очереди СБ/юриста, отключение своей MFA | Зашито в код (§5) |

Отказ по матрице — 403 «Недостаточно прав для этого действия — обратитесь к администратору системы» и событие журнала `permission_denied`; staff-ручка для не-сотрудника — 403 «Доступно только сотрудникам компании»; чужой объект — 403 «Нет доступа к этому объекту/проекту». Изменение матрицы или грантов действует со следующего запроса без перевыпуска сессий.

## 4. Матрица «роль × действие»

Обозначения: ✅ — можно (не настраивается); ⚙✅ — можно по умолчанию, право настраивается в матрице; ⚙ — по умолчанию нельзя, право можно выдать в матрице; ❌ — нельзя (не настраивается); **объект** — только на объектах из грантов пользователя; **своё** — только свои данные / своя организация. Столбец «Право» — код права матрицы или «код», если проверка зашита.

## 5. Права, зашитые в код (не настраиваются)

- Администратор обходит матрицу и грантов не требует; у него всегда «видит финансы»; ему нельзя снять права, сменить свою роль, отключить себя, отключить свою MFA.
- Пользователь контрагента, лид и владелец площадки — вне матрицы: их доступ задан контуром роли.
- Ролевые проверки внутри действий: ось «Проверка СБ» — только СБ и администратор; ось «Юридическая проверка» — только юрист и администратор; решение по квалификации контрагента — только администратор («Решение по квалификации выставляют администратор и руководитель тендерного отдела»); пул, опыт работ и дата аккредитации контрагента — только администратор и специалист; очередь СБ закрыта юристу, очередь юриста — СБ.
- Повторный ввод пароля: завершение тендера, отмена, перевыпуск и отзыв ссылки участника, сброс чужой MFA.
- Действия, доступные любому сотруднику без права матрицы: добавление единиц и синонимов, шаблоны тендеров, черновики мастера и разбор Excel, правка структуры тендера, раунды, документы, решения по корректировкам (при доступе к объекту), правка карточки контрагента.
- Раздел владельца — по признаку владельца, а не по роли.

## 7. Расхождения и рекомендации для воссоздания

1. **Интерфейс ролевой, сервер — по правам.** Меню и маршруты зависят от роли, а `/auth/me` не отдаёт список прав пользователя. Если администратор выдаст специалисту `users.manage` или `settings.manage`, сервер разрешит, но в интерфейсе пункта не будет; и наоборот — СБ и юрист видят административные разделы «Настроек», а сервер отвечает им 403. Требование: отдавать клиенту набор прав пользователя и строить меню и кнопки по правам (см. открытые вопросы).
2. **СБ и юрист технически могут менять структуру тендера, раунды, документы, корректировки** на объектах из своих грантов (проверка — только «сотрудник + объект»). По умолчанию грантов у них нет, поэтому на практике закрыто. Рекомендация: закрыть эти действия правом `tenders.manage`/`quotes.manage`.
3. **СБ и юрист могут править реквизиты и карточку контрагента**, шаблоны тендеров и единицы измерения — проверки ролей нет. Нужно решение Заказчика (см. открытые вопросы).
4. **Бюджетные позиции с суммами** читает любой сотрудник, включая СБ и юриста, хотя бюджет закрыт правом `budget.view`.
5. **Лид** попадает в список коллег для упоминаний и через API видит общие уведомления сотрудников; должен быть исключён.
6. **Владелец площадки** скрыт из реестра пользователей, но ручки правки пользователя по id его не исключают; требуется 404.
7. В реестре пользователей можно назначить роль `owner` или `lead` вручную; список назначаемых ролей надо ограничить.

## 8. Оценка

Ролевая модель, матрица прав, гранты и тесты матрицы доступа (для каждой роли — ожидаемые коды ответа ключевых ручек, включая попытку открыть чужой объект прямой ссылкой) — **M** сверх оценки домена учётных записей ([../02-business-logic/identity.md §12](../02-business-logic/identity.md#12-оценка-сложности)); перевод интерфейса с ролевой модели на права (п. 7.1) — ещё **S–M**.
