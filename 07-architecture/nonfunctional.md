# Нефункциональные требования

Производительность, доступность и health-check, логи, мониторинг и алерты, резервное
копирование и восстановление, поддерживаемые браузеры, локализация, доступность интерфейса
(a11y), требования к коду, тестам и git-хукам.

Связанные разделы: [архитектура](architecture.md), [масштабирование](scalability.md),
[безопасность](security.md), [демо-развёртывание](../08-deploy/demo-deploy.md),
[CI/CD](../08-deploy/ci-cd.md). Открытые вопросы — `../_oq/INFRA.md`.

Нумерация требований: **NFR-NN**. Метки сложности: **S / M / L / XL**.

## 1. Производительность

### 1.1. Бэкенд

| Параметр | Значение по умолчанию | Настройка | Поведение |
|---|---|---|---|
| Порог «медленного» ответа | 200 мс | `SLOW_REQUEST_MS` | Предупреждение в лог: метод, **шаблон** маршрута, статус, мс (и для упавших запросов) |
| Тайм-аут обработчика | 60 с | `REQUEST_TIMEOUT_SECONDS` | 504 `{"detail":"Запрос выполняется слишком долго — попробуйте сузить выборку"}`; отдача тела (SSE, выгрузки) не ограничена |
| Тайм-аут SQL-запроса (сервер) | 30 с | `DB_STATEMENT_TIMEOUT_MS` | Запрос прерывается Postgres, соединение возвращается в пул |
| Тайм-аут команды (клиент) | 30 с | `DB_COMMAND_TIMEOUT` | Страховка, если сервер не ответил |
| Ожидание соединения из пула | 30 с | `DB_POOL_TIMEOUT` | Явная ошибка вместо вечного ожидания |
| Сжатие | ≥ 1000 байт, уровень 6 | `GZIP_MIN_BYTES`, `GZIP_LEVEL` | Потоки `/stream` не сжимаются |
| Кэш тяжёлых чтений | 60 с | `HEAVY_READ_CACHE_SECONDS` | ETag + 304; готовые сжатые байты |
| Сторож фонового задания | 600 с | `PARSE_JOB_HANG_SECONDS` | Задание → `failed` с алертом |
| Опрос очереди | 1 с | `PARSE_JOB_POLL_INTERVAL` | Задержка старта задания ≤ 1 с при пустой очереди |

- **NFR-01.** Система должна отвечать на типовые интерактивные запросы (списки, карточки,
  сохранения) в пределах 200 мс на сервере при нагрузке, соответствующей
  [scalability.md §8](scalability.md#8-емкость-одной-реплики-оценка); всё, что дольше 60 с, —
  фоновым заданием с опросом статуса. **M**
- **NFR-02.** Сериализация крупных JSON-ответов — быстрым сериализатором (orjson или аналог);
  числа денежных сумм передаются без потери точности (решение о строках/числах фиксируется в
  [API](../04-api/openapi.json)).
- **NFR-03.** Тест «бюджета запросов»: число SQL-запросов на построение карточки тендера и
  сравнительной таблицы не растёт с числом участников и позиций (защита от N+1). **S**
- **NFR-04.** Условные GET (`If-None-Match` → 304) — для ленты уведомлений, сравнения и других
  частых чтений с длинными периодами без изменений.

### 1.2. Фронтенд (ориентиры исходной команды)

| Сценарий (тендер 898 позиций × 7 КП, прод-сборка, CPU ×4 замедления) | Ориентир |
|---|---|
| Переход «Обзор» → «Сравнение» | Интерактивность ≤ 500 мс, нет задач длиннее 200 мс |
| Открытие панели «Анализ ИИ» | Скрипт ≤ 50 мс, layout один раз на окончании анимации |
| Прокрутка таблицы | DOM ≈ видимое окно (виртуализация строк) |
| Фоновый опрос снимка | Только на видимой вкладке «Сравнение»; задача ≤ 50 мс |

- **NFR-05.** Экраны с крупными таблицами (СТ, ведомость, реестры) должны виртуализировать строки;
  каждый экран — отдельный чанк; тяжёлые библиотеки (графики) не попадают в общий чанк. **M**
- **NFR-06.** `refetchOnWindowFocus` выключен глобально; свежесть — точечными интервалами и
  инвалидацией после мутаций; опросы не идут на скрытой вкладке.

## 2. Доступность и health-check

### 2.1. Служебные ручки

| Ручка | Что проверяет | Ответ |
|---|---|---|
| `GET /api/health` | Процесс жив и принимает запросы | `{"status":"ok"}` |
| `GET /api/health/storage` | Хранилище: проба HEAD несуществующего ключа (проверяет сеть и ключи: чужой ключ даёт 403, а не 404), занятый объём по БД, счётчики процесса | `ok`, `error` (класс ошибки), `storage_backend`, `direct_upload`, `storage_used_bytes`, `counters` (`storage_uploads_total{status}`, `storage_s3_errors_total{op}`) |
| `GET /api/health/llm` | Путь до ИИ-шлюза: список моделей, наличие модели роли `mechanical`, пробный вызов на 1 токен (тайм-аут 30 с) | `ai_enabled`, `base_url`, `model`, `proxy`, `reachable`, `model_present`, `generate_ok`, `ok = ai_enabled ∧ reachable ∧ model_present` |

Закрытие служебных ручек от анонимов — [security.md SEC-51](security.md#10-заголовки-безопасности-и-периметр).

### 2.2. Healthcheck контейнеров

| Контейнер | Проверка | Интервал / тайм-аут / старт / попыток |
|---|---|---|
| backend | HTTP GET `http://127.0.0.1:8000/health` | 10 с / 3 с / **60 с** (перед uvicorn идут миграции) / 3 |
| frontend | HTTP GET `http://127.0.0.1:3000/` | 10 с / 3 с / 5 с / 3 |
| postgres | `pg_isready` по TCP (не по сокету: временный сервер initdb не должен считаться готовым) | 2 с / 3 с / — / 30 |
| хранилище, почта стенда | HTTP GET своего порта | 2 с / 3 с / — / 30 |

- **NFR-07.** Каждый контейнер имеет healthcheck и политику перезапуска `unless-stopped` (или
  эквивалент оркестратора); выкатка считается успешной только после `healthy` всех сервисов и
  ответа `/api/health` снаружи. **S**

### 2.3. Деградация вместо отказа

| Отказ | Поведение |
|---|---|
| ИИ выключен / шлюз недоступен / ответ не прошёл проверку | Детерминированный расчёт целиком + строка «Пояснения ИИ недоступны» |
| SMTP недоступен | Письмо не ушло — причина в следе доставки; задание повторяется с паузой |
| Хранилище недоступно | Отказ только загрузок/скачиваний; `/health/storage` → `ok:false`; остальной API работает; сбой создания бакета на старте не валит старт |
| БД недоступна до 60 с (рестарт при выкатке) | Воркер пишет предупреждения без алертов, продолжает на следующем тике |
| Хранилище счётчиков лимитов недоступно | Вход/восстановление — 503 (fail-closed); прочие ручки — окно в памяти процесса |
| Слушатель `LISTEN` оборвался | Переподключение 1 → 30 с, затем `resync` всем потокам |
| Антивирус включён и недоступен | Отказ загрузки (не пропуск) |
| Telegram/SIEM/приёмник логов недоступны | Предупреждение в лог; SIEM и логи — повтор с того же курсора |

- **NFR-08.** Целевая доступность (SLA), окна обслуживания и допустимый простой при выкатке
  согласуются с Заказчиком (см. открытые вопросы). Текущая выкатка пересоздаёт контейнеры —
  кратковременный простой (секунды–минута) неизбежен; для выкатки без простоя нужны ≥ 2 реплики за
  балансировщиком и миграции, совместимые с предыдущей версией кода. **M**

## 3. Логи

- **NFR-09.** Логи — в stdout/stderr контейнера; формат `LOG_FORMAT`: `text`
  (`2026-10-15T09:30:00 INFO [app] сообщение`) или `jsonl` (`ts`, `level`, `logger`, `msg`,
  `request_id`, `exc`). Поля JSON не расширяются содержимым записи. **S**
- **NFR-10.** Уровни: DEBUG, INFO (по умолчанию), WARNING, ERROR, CRITICAL; неизвестное значение —
  отказ старта. Обязательно логируются: старт с редактированным снимком конфигурации, медленные
  ответы, тайм-ауты, необработанные исключения с трейсбэком, жизненный цикл заданий (`job start /
  done / failed / requeued` с id, типом, попыткой и `request_id`), смена лидера очереди,
  состояние канала realtime.
- **NFR-11.** В логах не должно быть: паролей, токенов (в т.ч. в URL — логгеры HTTP-клиента на
  уровне WARNING), значений шифруемых полей, тел КП и промптов ИИ. Тест «секреты не попадают в
  лог» обязателен. **S**
- **NFR-12.** Каждая строка, порождённая запросом, несёт `request_id`, совпадающий с заголовком
  `X-Request-Id` ответа и `correlation_id` журнала ИБ; фоновое задание хранит `request_id`
  породившего запроса.
- **NFR-13.** На сервере должна быть настроена ротация логов контейнеров (ограничение размера и
  числа файлов драйвера логов или сборщик логов) и отдельный том под логи. Срок хранения техлогов
  — по согласованию (ориентир 30 дней).

## 4. Мониторинг и алерты

Что есть в исходной системе:

| Механизм | Что ловит |
|---|---|
| Техалерты в Telegram (`ALERTS_ENABLED`) | Необработанная ошибка запроса (500), падение фонового задания, зависание задания; дедуп 300 с со счётчиком подавленных; в тексте — хост, `request_id`, `job_id`, класс ошибки |
| Паттерны логов → Telegram | Правила в БД: уровень, подстрока/регулярное выражение, окно (мин), порог, ключ дедупа; правятся в интерфейсе без выкатки |
| Журнал медленных ответов | Строки `slow …` в логе |
| `/health/*` | Внешний мониторинг доступности |
| Просмотр логов контейнеров | Веб-просмотрщик логов Docker на демо-стенде |

- **NFR-14.** В воссоздаваемой системе рекомендуется добавить метрики в формате Prometheus/OpenMetrics
  (закрытая ручка или порт): RPS и латентность по шаблону маршрута, коды ответов, занятость пула
  БД, глубина очереди заданий по типам и время выполнения, число открытых SSE-потоков, вызовы ИИ
  (длительность, ошибки, токены), загрузки (успех/отказ по причине). **M**
- **NFR-15.** Минимальный набор алертов: недоступность `/api/health` дольше 2 мин; доля 5xx > 2 %
  за 5 мин; p95 латентности > 1 с за 10 мин; задания в `queued` старше 5 мин; `failed`-задания
  почты; свободное место на томе БД/логов < 15 %; отсутствие свежей резервной копии за сутки;
  `/health/storage` → `ok:false`. Каналы — Telegram и/или email. **S**

## 5. Резервное копирование и восстановление

### 5.1. Как сделано в исходной системе (для стенда)

- **Снятие:** `pg_dump -Fc` базы целиком в файл + синхронизация всех объектов бакета в каталог и
  упаковка в tar. Пишется во временные файлы и переименовывается только после успеха обоих шагов
  (в хранилище не попадает недорезанный дамп).
- **Отметка:** после снятия/накатки в базе ставится `COMMENT ON DATABASE <db> IS 'dump <sha256 файла
  дампа>'` — по ней видно, какой дамп накатан (отметка пропадает вместе с томом БД).
- **Восстановление:** бэкенд останавливается; одной транзакцией выполняется `BEGIN; DROP SCHEMA
  public CASCADE; CREATE SCHEMA public;` + поток `pg_restore --no-owner --no-acl -f -`, и `COMMIT`
  отправляется **только если pg_restore дочитал дамп до конца** (иначе откат — остаётся старая
  база, не пустая); затем файлы из архива синхронизируются в бакет (существующие объекты не
  удаляются), ставится отметка, бэкенд запускается и сам доводит схему миграциями. При любом
  исходе бэкенд, работавший до операции, запускается снова.

### 5.2. Требования к продуктиву

- **NFR-16.** Ежедневная резервная копия БД (логический дамп `-Fc` или физическое копирование с
  архивом WAL для восстановления на момент времени) и копия объектного хранилища (версионирование
  бакета и/или репликация в другое хранилище); копии хранятся вне сервера приложения. **M**
- **NFR-17.** Ключ шифрования полей (`FIELD_ENCRYPTION_KEY`) и остальные секреты хранятся
  отдельно от дампов, но так, чтобы их можно было восстановить: дамп без ключа — нечитаемые ПДн и
  секреты MFA.
- **NFR-18.** Процедура восстановления оформлена скриптом/командой (как выше: одна транзакция,
  коммит только при полном чтении дампа, отметка sha256, миграции на старте) и проверяется
  восстановлением на отдельный стенд не реже раза в квартал. **S**
- **NFR-19.** RPO, RTO и срок хранения копий согласуются с Заказчиком (см. открытые вопросы);
  ориентир при отсутствии требований: RPO ≤ 24 ч, RTO ≤ 4 ч, хранение 14 ежедневных и 6
  ежемесячных копий.

## 6. Поддерживаемые браузеры

Явного списка (browserslist) в сборке исходной системы нет; цель сборки — умолчание Vite. По
используемым технологиям фактический минимум:

| Ограничение | Откуда |
|---|---|
| Chrome / Edge 111+, Safari 16.4+, Firefox 128+ | Tailwind CSS 4 (вендоренные компоненты) |
| Нативный `<dialog>`, Web Locks API, BroadcastChannel, `fetch`-потоки | Модальные окна, лидер вкладок, SSE-клиент |

- **NFR-20.** Предлагаемый ориентир до ответа Заказчика: система работает в двух последних
  мажорных версиях Chrome, Edge, Firefox, Safari (десктоп) и Яндекс Браузера (Chromium) не ниже
  минимума из таблицы. Каркас исходной системы адаптирован под устройства с касанием
  (`pointer: coarse`, `hover: none`) без изменения десктопной сетки; требования к мобильным
  экранам и минимальной ширине окна — открытый вопрос. **S**

## 7. Локализация и время

- **NFR-21.** Интерфейс, письма, выгрузки, тексты ошибок API — только на русском языке;
  мультиязычность не требуется. **S**
- **NFR-22.** Время хранится в БД как `timestamptz` (UTC), контейнеры работают в UTC; моменты
  времени показываются пользователю по Москве (`Europe/Moscow`, МСК), календарные даты (фильтры,
  «текущий год») — по местному времени браузера. Сроки (дедлайны раундов) задаются и
  отображаются в МСК.
- **NFR-23.** Числа и суммы — в русском формате (пробел — разделитель разрядов, запятая —
  десятичный, `₽`); ставка НДС — настройка `VAT_RATE_PCT` (22), а не константа в текстах.

## 8. Доступность интерфейса (a11y)

Что есть в исходной системе: ссылка «Перейти к содержимому» первым элементом каждого каркаса
(WCAG 2.4.1); перенос фокуса на заголовок нового экрана после перехода внутри SPA (WCAG 2.4.3,
кроме первой загрузки, смены только `?query` и случая, когда фокус уже переставил экран или
человек); модальные окна и выпадающие меню на нативном `<dialog>` (фокус-ловушка, Esc);
ARIA-атрибуты у интерактивных элементов; учёт `prefers-reduced-motion`.

- **NFR-24.** Все действия выполнимы с клавиатуры, видимый фокус (`:focus-visible`), порядок
  табуляции соответствует визуальному, модальные окна возвращают фокус на вызвавший элемент. **M**
- **NFR-25.** Целевой уровень — WCAG 2.1 AA для экранов сотрудников и контрагента (контраст,
  подписи полей, сообщения об ошибках, связанные с полем); уровень подтверждается Заказчиком
  (см. открытые вопросы).

## 9. Требования к коду и тестам

### 9.1. Бэкенд

- **NFR-26.** Тесты — pytest с **реальным PostgreSQL** (JSONB, `ON CONFLICT`, триггеры): отдельная
  тестовая база (создаётся автоматически), схема строится из моделей, каждый тест — в транзакции
  с откатом. Тесты без доступной БД **пропускаются** — поэтому в CI/хуках число пропусков должно
  быть нулевым (иначе прогон считается проваленным). **M**
- **NFR-27.** Общая настройка тестов — один плагин: окружение задаётся до импорта приложения,
  переменные контейнера/`.env` вычищаются (тесты видят умолчания кода), вызывается корень
  композиции; ИИ принудительно выключен, тест ИИ явно включает его и подменяет транспорт (сеть в
  тестах запрещена); S3 — эмулятор в тестах (moto или аналог).
- **NFR-28.** Обязательные группы тестов: архитектура (слои и домены по импортам; сверка индексов
  моделей и схемы; «нет пакетов вне доменов»), матрица доступа по ролям, инварианты
  безопасности, платформа (лимиты, лидер воркера, шифрование, проверки старта, секреты в логах,
  почта, валидация, зеркало валидации), хранилище (общий контракт local/s3, прямая загрузка),
  бюджет запросов, ИИ (с заглушкой шлюза), e2e ключевых сценариев. Исходная система: 191 файл тестов.
- **NFR-29.** Линтер и форматтер (ruff: правила E, F, I, UP, B; длина строки 110) обязательны;
  статическая типизация (mypy) — желательна.

### 9.2. Фронтенд

- **NFR-30.** Юнит/компонентные тесты — vitest + Testing Library в jsdom (`*.test.ts(x)`), для
  файлов с «тихими» ошибками (разбор SSE, тексты ошибок, перенос фокуса, валидация, жизненный цикл
  тендера) — 100 % покрытия строк, веток и функций **по каждому файлу** (не суммарно). Исходная
  система: 111 файлов тестов. **M**
- **NFR-31.** Assert-скрипты (`*.check.ts`, запускаются рантаймом без раннера) — для инвариантов
  чистых функций (разбор дат, ранжирование сравнения, монотонность ширин колонок); исходная
  система — 64 скрипта.
- **NFR-32.** Линтер с проверкой границ FSD (oxlint или ESLint с ограничением импортов),
  форматтер, `tsc --noEmit` как часть сборки (`build` = проверка типов + сборка).

### 9.3. Git-хуки и CI

- **NFR-33.** Хуки ставятся одной командой после клонирования и выполняются в контейнере (на хосте
  нет тулчейна):

| Стадия | Бэкенд | Фронтенд |
|---|---|---|
| pre-commit | пробелы/концы файлов, синтаксис YAML/TOML, маркеры конфликтов, крупные файлы (≤ 20 МБ — дамп стенда хранится в репозитории), приватные ключи, сканер секретов, проверка форматирования, линтер, тесты архитектуры | то же (крупные файлы ≤ 1 МБ, JSON), сканер секретов, линтер с границами FSD, проверка типов |
| pre-push | полный pytest (поднимает инфраструктуру стенда) | vitest, assert-скрипты, полная сборка |

- **NFR-34.** CI сборки образов в исходной системе **не** запускает тесты и линтер (только сборку
  образа; во фронте сборку валит `tsc`). Исполнитель должен добавить в CI обязательный прогон
  линтеров, тестов (с сервисом Postgres) и тестов архитектуры перед сборкой образа; см.
  [ci-cd.md](../08-deploy/ci-cd.md). **M**
- **NFR-35.** Совпадение правил валидации бэкенда и фронтенда проверяется сравнением общих
  наборов тестовых значений (задача корневого репозитория).
