# Безопасность

Требования к аутентификации, авторизации, защите от CSRF, доверенным прокси, журналу ИБ,
шифрованию персональных данных, секретам, приёму файлов, обработке данных ИИ, заголовкам
безопасности, серверам Заказчика и соответствию законодательству о персональных данных.

Связанные разделы: [архитектура](architecture.md), [нефункциональные требования](nonfunctional.md),
[демо-развёртывание](../08-deploy/demo-deploy.md), [ИИ](../06-ai/), [модель данных](../05-data-model/),
[бизнес-логика](../02-business-logic/). Открытые вопросы — `../_oq/INFRA.md`.

Нумерация требований: **SEC-NN**. Метки сложности: **S / M / L / XL**.

---

## 1. Аутентификация

### 1.1. Транспорт сессии — только HttpOnly-cookie

Заголовка `Authorization` с токеном у браузерного клиента нет; JavaScript не имеет доступа к
токенам.

| Cookie | Содержимое | Путь | Срок |
|---|---|---|---|
| `tendo_at` | JWT доступа (HS256) с claim `sid` (сессия) и отпечатком пароля | `/api/` (префикс API + `/`) | `ACCESS_TOKEN_MINUTES` (15) мин + 60 с |
| `tendo_rt` | Непрозрачный refresh-токен; в БД (`auth_sessions`) хранится только его хеш | `/api/auth` — не уезжает с обычными запросами | до конца скользящего срока простоя (`SESSION_IDLE_DAYS`, 14 сут), но не дальше абсолютного потолка |
| `tendo_mfa` | Одноразовый челлендж второго фактора | `/api/auth/login/mfa` | `MFA_CHALLENGE_MINUTES` (5) мин |

Все три: `HttpOnly`, `SameSite=Lax`, `Secure` (флаг `COOKIE_SECURE`, отключается только для
голого http на loopback при локальной отладке). Путь cookie строится из `root_path` (API живёт
под префиксом `/api`).

- **SEC-01.** Система должна аутентифицировать браузер только через HttpOnly-cookie с указанными
  атрибутами; токены не должны попадать в `localStorage`, URL и логи. **M**

### 1.2. Сессии и refresh-ротация

- **SEC-02.** Каждый вход создаёт запись сессии устройства (`auth_sessions`: хеш refresh, срок
  простоя, абсолютный срок, отзыв, IP/устройство). Каждый запрос сверяет `sid` из JWT с живой
  записью — выход, «выйти на всех устройствах», деактивация и смена пароля действуют сразу, а не
  через остаток 15 минут. Ответ — 401 «Сессия завершена. Войдите заново.».
- **SEC-03.** Refresh вращается при каждом `POST /auth/refresh`. Повтор **старого** значения в
  окне 30 с (гонка вкладок) выдаёт только новый токен доступа; повтор позже считается кражей:
  сессия закрывается, в журнал ИБ пишется событие повторного использования. **M**
- **SEC-04.** Срок сессии скользящий — `SESSION_IDLE_DAYS` (14) дней простоя — и абсолютный
  потолок `SESSION_ABSOLUTE_DAYS` (30) дней. Выход по неактивности — событие
  `session_idle_timeout`, текст «Сессия завершена из-за неактивности. Войдите снова.».
- **SEC-05.** Смена пароля завершает все сессии пользователя (JWT несёт отпечаток хеша пароля):
  «Сессия завершена: пароль был изменён. Войдите заново.».
- **SEC-06.** Клиент обновляет сессию одним запросом на браузер (очередь через Web Locks между
  вкладками) и повторяет исходный запрос.

### 1.3. Вход и защита от перебора

- **SEC-07.** Вход — email, затем пароль (bcrypt, проверка в пуле потоков). Ошибка — единый
  текст «Неверный email или пароль» без раскрытия существования учётки.
- **SEC-08.** После `MAX_FAILED_LOGIN_ATTEMPTS` (5) неудач подряд пара «учётка + IP» получает
  нарастающую паузу 1, 2, 4, … минут, не больше `LOGIN_THROTTLE_MAX_MINUTES` (60). Учётка целиком
  не блокируется (чужой адрес не должен запирать владельца); администратор может снять паузу.
  Пауза хранится в БД (`login_throttle`), а не в памяти процесса. **M**
- **SEC-09.** Ручки входа и восстановления дополнительно ограничены по частоте с режимом
  **fail-closed** (при недоступном хранилище счётчиков — 503, а не «без лимита»); значения — в
  [scalability.md §6.2](scalability.md#62-лимиты-частоты).
- **SEC-10.** Восстановление пароля: ответ всегда «Если учётная запись существует, мы отправили
  письмо со ссылкой.»; ссылка одноразовая, живёт 2 ч; ссылка активации новой учётки — 72 ч. В БД —
  только хеши одноразовых токенов.

### 1.4. Второй фактор (MFA)

- **SEC-11.** MFA — TOTP (RFC 6238, приложение-аутентификатор, QR-код с издателем `TOTP_ISSUER`
  или `BRAND_NAME`). Секрет TOTP хранится зашифрованным (§6). Повтор уже использованного кода
  отсекается (номер последнего принятого интервала у пользователя). **M**
- **SEC-12.** Шаг MFA после пароля — запись `login_challenges` в БД (одноразовая, 5 мин, не более
  5 неверных кодов), а не память процесса: процессов и реплик несколько.
- **SEC-13.** Для роли администратора и для владельца площадки MFA обязательна (`MFA_ENFORCED`,
  по умолчанию `true`): пока второй фактор не настроен, сервер пропускает только профиль и ручки
  настройки MFA (403 «Для продолжения работы настройте двухфакторную аутентификацию»), фронт
  принудительно ведёт на настройку.
- **SEC-14.** Сброс MFA пользователю выполняет администратор с **повторным вводом своего пароля**
  (заголовок подтверждения; без него — 403 «Подтвердите действие паролем», неверный — 403
  «Пароль не подошёл — действие не выполнено»). Тот же механизм подтверждения — для отдельных
  необратимых действий с тендером.

### 1.5. Политика паролей

- **SEC-15.** Пароль должен: **S**
  - иметь длину 8–64 символа и не более 72 байт в UTF-8 (предел bcrypt; кириллица — 2 байта);
  - не начинаться и не заканчиваться пробелом;
  - содержать символы минимум трёх категорий из четырёх: строчные, прописные, цифры, спецсимволы
    (кириллица учитывается);
  - не входить в список распространённых паролей; содержать не менее 4 разных символов;
  - не содержать локальную часть email (от 3 символов) и части имени (от 4 символов);
  - не совпадать с текущим паролем и с 5 предыдущими (история хешей — 5 записей).

  Тексты ошибок — на русском, по одному на правило (образцы: «Пароль должен быть не короче 8
  символов», «Пароль должен содержать символы минимум трёх категорий: строчные, прописные,
  цифры, спецсимволы», «Этот пароль слишком распространён — придумайте другой»).
- **SEC-16.** Правила валидации (пароль, телефон, email, ИНН, ОГРН, адрес) реализуются
  одинаково на фронте и бэкенде; совпадение наборов тестовых значений проверяется автоматически
  (общий JSON-набор «зеркала» правил).

### 1.6. Особые учётные записи

- **SEC-17.** Владелец площадки (суперадмин, признак `is_superadmin`) заводится только
  CLI-командой в контейнере бэкенда; ему доступны только `/auth/*` и раздел владельца `/owner*`
  (остальное — 403 «Раздел недоступен учётной записи владельца площадки»).
- **SEC-18.** **Миграции не должны создавать учётные записи с известным паролем.** В исходной
  системе начальная миграция заводит демо-учётки всех ролей с общим слабым паролем — в
  воссоздаваемой системе демо-данные загружаются только отдельным шагом для демо-стенда, а первый
  администратор Заказчика создаётся CLI-командой с одноразовым паролем и обязательной сменой при
  первом входе. **S**

## 2. Авторизация

### 2.1. Роли

| Код | Роль | Контур |
|---|---|---|
| `admin` | Администратор | Сотрудник; матрица прав его не ограничивает (не может запереть систему) |
| `tender_specialist` | Тендерный специалист | Сотрудник; видит только назначенные портфели/проекты |
| `security` | Служба безопасности | Сотрудник; реестр контрагентов, свои проверки, журнал ИБ |
| `lawyer` | Юрист | Сотрудник; реестр контрагентов, свои проверки |
| `supplier` | Пользователь контрагента | ЛК поставщика; матрица не применяется, доступ ограничен своей организацией |
| `lead` | Лид (заявка с лендинга, если включено) | Прав нет; видит экран ожидания назначения |
| `owner` | Владелец площадки | Вне ролей Заказчика; только раздел владельца |

### 2.2. Матрица «роль × действие»

Список действий — константа в коде; в БД хранятся только выданные отметки. Действие проверяется
на сервере в каждом роутере (`Perm(...)`); интерфейс скрывает недоступное, но решает сервер.

| Право | Смысл | По умолчанию у |
|---|---|---|
| `portfolios.manage` | Создавать и изменять портфели и объекты | тендерный специалист |
| `tenders.manage` | Создавать тендеры и приглашать контрагентов | тендерный специалист |
| `quotes.manage` | Обрабатывать КП | тендерный специалист |
| `suppliers.manage` | Удалять/восстанавливать контрагентов, выдавать доступ в ЛК | — |
| `suppliers.contacts.view` | Видеть полные контакты контрагента (иначе маска) | тендерный специалист, СБ, юрист |
| `reports.view` | Отчёты и выгрузки | тендерный специалист |
| `finance.view` | Цены и финансовые данные | — |
| `budget.view` / `budget.manage` | Смотреть / распределять бюджет | тендерный специалист (view) |
| `catalogs.manage` | Справочники | — |
| `users.manage` | Пользователи и их доступ к объектам | — |
| `security.manage` | Журнал ИБ, инциденты, выгрузки для регулятора | СБ |
| `settings.manage` | Настройки системы | — |
| `billing.view` | Расходы на ИИ | — |

Администратор имеет все права всегда; строки ролей `admin`, `supplier`, `owner` в матрице не
редактируются (с пояснением в интерфейсе). Изменение прав роли — событие журнала ИБ.

- **SEC-19.** Система должна проверять права на сервере для каждой ручки; отказ — 403
  «Недостаточно прав для этого действия — обратитесь к администратору системы»; staff-ручки для
  контрагента — 403 «Доступно только сотрудникам компании». Отказ пишется в журнал ИБ
  (`permission_denied`). **M**
- **SEC-20.** Доступ к данным тендера, КП, бюджета и чатов ограничен **деревом портфелей**:
  тендерный специалист видит только портфели/проекты из своих грантов
  (`user_portfolio_access`, `user_project_access`); администратор — всё. Проверка выполняется в
  сервисе при каждом чтении и записи, включая выгрузки, ИИ-разбор и сохранённую историю анализа.
  **L**
- **SEC-21.** Пользователь контрагента видит только данные своей организации (`/me/*`) и
  тендеры, куда она приглашена; приостановка организации закрывает все её сессии (403 «Доступ
  организации приостановлен…»). Контуры не пересекаются: пользователь ЛК не получает
  staff-роль ни одним путём.
- **SEC-22.** Маска контактов контрагента (`CONTACTS_MASK_ENABLED`, по умолчанию выключена):
  включённая — полные ИНН, почта, телефон видны только с правом `suppliers.contacts.view`,
  остальным — маска (ИНН `78•••••252`: 2 первые и 3 последние цифры, при длине меньше 8 — целиком
  скрыт; почта — первая буква и 5 точек до `@`; телефон — код и 2 последние цифры). Одна функция
  маски на экран сравнения, выгрузку СТ и протокол.
- **SEC-23.** Тесты матрицы доступа: для каждой роли — ожидаемые коды ответа ключевых ручек
  (позитивные и негативные), включая попытку открыть чужой объект прямой ссылкой. **M**

### 2.3. Ссылки без учётной записи (magic-link)

- **SEC-24.** Форма КП, анкета саморегистрации и чат контрагента по ссылке работают по
  случайному токену (не менее 122 бит энтропии). Перевыпуск ссылки гасит старый токен. Публичные
  ручки по токену ограничены по частоте (по IP и по паре «токен + IP») и суточными квотами
  сообщений/вложений на тред. Рекомендуется хранить в БД хеш токена, а не сам токен (в исходной
  системе токен ссылки-приглашения на анкету шифруется, токен приглашения в тендер хранится как
  есть). **S**

## 3. CSRF и CORS

- **SEC-25.** Защита от CSRF: `SameSite=Lax` у всех cookie плюс проверка заголовка `Origin` на
  небезопасных методах (POST/PUT/PATCH/DELETE): чужой origin (не из `CORS_ORIGINS` и не
  `PUBLIC_APP_URL`) — 403 «Запрос с чужого источника отклонён». Запрос без `Origin` (не браузер)
  пропускается. **S**
- **SEC-26.** CORS: явный список `CORS_ORIGINS` (пустой или `*` — отказ старта),
  `allow_credentials`, ограниченный набор заголовков (см. [architecture.md §9](architecture.md#9-сквозная-обработка-запроса-middleware)).
  SPA и API рекомендуется держать на одном домене (API под `/api`), тогда CORS нужен только
  дополнительным источникам (например, лендингу).

## 4. Доверенные прокси и IP клиента

- **SEC-27.** Бэкенд доверяет `X-Forwarded-For`/`X-Forwarded-Proto` только от прокси из
  `FORWARDED_ALLOW_IPS` — по умолчанию loopback и частные сети RFC 1918 (сети Docker). IP клиента
  берётся справа налево — первый недоверенный адрес. Значение `*` запрещено: с ним клиент
  подделывает IP заголовком и обходит лимиты входа. Если прокси вне частных сетей — его адрес
  задаётся явно. **S**
- **SEC-28.** HSTS выставляется только если запрос пришёл по HTTPS (схема или
  `X-Forwarded-Proto: https`).

## 5. Аудит и журнал ИБ

- **SEC-29.** Все значимые действия пишутся в журнал ИБ `security_audit_log` по **закрытому
  каталогу событий** (неизвестный код события — ошибка разработчика). Каталог разбит на 11
  категорий: «Аутентификация и доступ», «Пользователи и роли», «Отчёты и чувствительные
  просмотры», «Шифрование и ИБ-операции», «Контрагенты и тендеры», «ИИ и автоматизация»,
  «Справочники и бюджет», «Портфели и проекты», «Шаблоны», «Биллинг», «Наблюдаемость». Состав событий — в
  [бизнес-логике](../02-business-logic/). **M**
- **SEC-30.** Журнал — **append-only на уровне БД**: триггеры запрещают `UPDATE` и `DELETE`
  (аналогично — история квалификации контрагента). Каждое событие несёт `correlation_id` = сквозной
  `X-Request-Id`, автора, IP, время.
- **SEC-31.** Правила автоинцидентов (класс события, порог, окно) заводят инцидент; событие
  «инцидент создан» доставляется письмом носителям права `security.manage` фоновым заданием.
- **SEC-32.** Передача журнала во внешний SIEM (опционально; в интерфейсе скрыта флагом сборки):
  дренаж по курсору пачками до 1000 событий в NDJSON одним POST; курсор двигается только после
  успеха — недоступный коллектор ничего не теряет. Заголовок авторизации SIEM наружу (API,
  снимок конфигурации) не отдаётся — только признак «задан».
- **SEC-33.** Выгрузки журнала (в т.ч. текстовая) и пакеты сведений для регулятора — с правом
  `security.manage`, сама выгрузка — событие журнала.

## 6. Шифрование персональных данных в БД

- **SEC-34.** Чувствительные поля шифруются прозрачно на уровне слоя доступа к данным (сервисы
  работают с открытыми строками). Формат шифротекста — `v1:<провайдер>:<payload>` (версия и метка
  провайдера — для будущей ротации и аудита). **M**

| Таблица | Поле | Причина |
|---|---|---|
| Контрагенты | ФИО руководителя, телефон, email организации | ПДн |
| Контакты контрагента | ФИО, телефон, email | ПДн представителя |
| Пользователи | секрет TOTP | секрет второго фактора |
| Настройки SMTP | пароль | секрет |
| Приглашения на саморегистрацию | токен ссылки | дамп БД не должен давать рабочих ссылок |

Сознательно **не** шифруются ИНН и ОГРН (поиск и автопроверки).

- **SEC-35.** Текущий провайдер — Fernet (AES-128-CBC + HMAC-SHA256) с ключом
  `FIELD_ENCRYPTION_KEY`; **это не сертифицированное СКЗИ**. Система при старте пишет
  предупреждение, а экран статуса шифрования (СБ) показывает провайдера, алгоритм, признак
  сертификации, результат самотеста и перечень шифруемых/нешифруемых полей. Подключение
  сертифицированного ГОСТ-средства должно сводиться к замене одного модуля-провайдера с тем же
  интерфейсом `encrypt/decrypt`.
- **SEC-36.** Нерасшифровываемое значение (чужой ключ, неизвестный провайдер) не отдаётся наружу
  сырым шифротекстом: для кода это пустая строка с причиной, при пересохранении записи исходный
  шифротекст возвращается в колонку без изменений; пустое значение поверх нерасшифрованного не
  стирает его. В лог — одно предупреждение на поле, без значения. Письмо на нерасшифрованный адрес
  не уходит («Адрес не расшифрован»).
- **SEC-37.** Значения без префикса версии читаются как открытый текст (наследие до включения
  шифрования) и шифруются при следующей записи.
- **SEC-38.** Ротация ключа шифрования полей должна выполняться CLI-командой перешифрования
  (в исходной системе её нет — есть только отчёт о нерасшифровываемых значениях). **M** — см.
  открытые вопросы.

## 7. Секреты и их ротация

| Секрет | Назначение | Последствия ротации |
|---|---|---|
| `JWT_SECRET` | Подпись JWT доступа | Все токены доступа недействительны; refresh-сессии живы — клиенты незаметно обновятся |
| `FIELD_ENCRYPTION_KEY` | Шифрование полей | Без перешифрования данные становятся нечитаемыми (SEC-38) |
| `DATABASE_URL` | Подключение к БД (с паролем) | Перезапуск бэкенда |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | Хранилище | Перезапуск; выданные presigned-ссылки перестают работать |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | Почта | Перезапуск (или правка в интерфейсе при `SMTP_SETTINGS_IN_UI`) |
| `AI_API_KEY` | ИИ-шлюз | Перезапуск |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | Алерты | Перезапуск |
| `LOG_FORWARD_TOKEN` | Приёмник логов | Перезапуск |
| `GITHUB_BUGREPORT_TOKEN`, `GITHUB_BUGREPORT_WEBHOOK_SECRET` | Трекер задач для баг-репортов, подпись вебхука | Перезапуск |
| `POSTGRES_PASSWORD` (инфраструктура) | Учётка БД | Смена в БД и в `DATABASE_URL` |

- **SEC-39.** Секреты задаются только переменными окружения (или менеджером секретов, который их
  подставляет); в репозитории и YAML их нет; публичные dev-значения из репозитория отвергаются
  при старте; снимок конфигурации в логе маскирует все секреты. В git-хуках работает сканер
  секретов (gitleaks или аналог). **S**
- **SEC-40.** Секреты генерируются криптографически стойко: `JWT_SECRET` — не менее 32 случайных
  байт; `FIELD_ENCRYPTION_KEY` — 32 случайных байта в urlsafe-base64 (формат Fernet).
- **SEC-41.** Регламент ротации (периодичность, ответственные) согласуется с СБ Заказчика — см.
  открытые вопросы.

## 8. Загрузка файлов

- **SEC-42.** Сервер проверяет каждый файл (браузерная подсказка `accept` — не контроль): **M**
  1. имя очищается: срезается путь (`../`, `C:\`), управляющие символы, ведущие точки, длина до
     200 символов; пустое — `file.bin`;
  2. расширение — из белого списка: PDF, PNG, JPG/JPEG, GIF, WEBP, DOC, DOCX, XLS, XLSX, XLSM, ZIP,
     RAR, 7Z, TXT, CSV; иначе 400 «Такой тип файла не принимается. Можно: …»;
  3. заявленный тип совпадает с расширением (или не заявлен/`application/octet-stream`); иначе 400
     «Тип файла не совпадает с его расширением»;
  4. размер: пустой — 400 «Пустой файл»; больше `MAX_UPLOAD_MB` (25) — 413 «Файл больше 25 МБ»;
     Excel мастера тендера — до 50 МБ (413 «Файл слишком большой (максимум 50 МБ). Разбейте
     таблицу или удалите лишние листы.»);
  5. первые 16 байт совпадают с сигнатурой формата (переименованный исполняемый файл
     отклоняется): 400 «Содержимое файла не совпадает с его типом»;
  6. антивирус (если включён).
- **SEC-43.** Сохраняется **канонический** тип расширения, а не присланный: presigned GET отдаёт
  его в `Content-Type`, `Content-Disposition` — с безопасным именем, так что подсунуть
  `text/html` через `x.pdf` нельзя.
- **SEC-44.** Антивирус: `VIRUS_SCANNER=clamav` + `CLAMAV_HOST`/`CLAMAV_PORT` — clamd по TCP
  командой INSTREAM, файл идёт потоком из хранилища, тайм-аут 60 с. Найдена сигнатура — отказ.
  **Недоступный антивирус — отказ загрузки**, а не пропуск (выключенный антивирус не должен быть
  неотличим от чистого файла). По умолчанию `noop`. **S**
- **SEC-45.** Доступ к вложению проверяется через доступ к сущности-владельцу (тендер, КП,
  контрагент, чат), а не только по идентификатору файла. Presigned-ссылки — короткоживущие
  (15 мин). Бакет не публичный; CORS бакета — только origin приложения, методы PUT/GET/HEAD,
  заголовок `Content-Type`.

## 9. ИИ и утечка данных

- **SEC-46.** При включённом ИИ содержимое сравнительной таблицы (позиции, цены, условия,
  комментарии поставщиков) уходит во внешний шлюз. Требования: **M**
  - в запрос включаются только поля, нужные секции анализа; учётные данные, контакты, ФИО и
    исходные вложения исключаются;
  - текст поставщика и пользователя передаётся в обёртке недоверенных данных, отдельно от
    системных инструкций (защита от prompt injection); модель не исполняет указаний из него;
  - каждое число в ответе модели сверяется с детерминированной таблицей, непроверяемые пункты
    отбрасываются; исполняются только разрешённые действия экрана;
  - ИИ ничего не отправляет контрагентам (письмо — черновик);
  - тексты промптов и ответов хранятся только при `AI_PROMPT_LOG_ENABLED` и стираются через
    `AI_PROMPT_LOG_DAYS` (30) дней; в техлог payload не попадает;
  - сохранённый разбор помечается профилем обработки (куда ушли данные), моделью и версией
    промпта; это видно в журнале.
- **SEC-47.** Площадка обработки ИИ (облачный шлюз, отечественный провайдер или локальная модель
  через OpenAI-совместимый API) — договорное решение Заказчика; при запрещённом контуре ИИ
  выключается (`AI_ENABLED=false`) без потери функций расчёта. Исходящий доступ к шлюзу — только
  через `AI_HTTP_PROXY`, если так требует контур.
- **SEC-48.** `GET /health/llm` не должен быть анонимным в проде: он делает платный пробный вызов
  и раскрывает адрес шлюза и прокси (в исходной системе ручка публичная). Рекомендуется закрыть
  правом администратора или доступом только из внутренней сети. **S**

## 10. Заголовки безопасности и периметр

- **SEC-49.** Каждый ответ API несёт: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(),
  geolocation=()`, за TLS — `Strict-Transport-Security: max-age=31536000; includeSubDomains`. **S**
- **SEC-50.** Рекомендуется (в исходной системе нет): `Content-Security-Policy` для SPA на уровне
  раздачи статики (`default-src 'self'`, `connect-src 'self'` + адрес хранилища, `img-src 'self'
  data: blob:` + адрес хранилища, `frame-ancestors 'none'`). **S**
- **SEC-51.** Swagger UI и схема OpenAPI на проде — только для аутентифицированных
  администраторов или из внутренней сети; `/health` — публичный (только `{"status":"ok"}`);
  `/health/storage` и `/health/llm` — не публичные (раскрывают объём и адреса). **S**

## 11. Требования к серверам Заказчика (обобщённо)

Перед развёртыванием в контуре Заказчика выполняется последовательность (повторяется для
каждого развёртывания):

1. **Требования СБ Заказчика** — запросить письменно и разложить в таблицу «требование → чем
   закрыто → что доделать». Это вход для всех остальных шагов.
2. **Проверка доступа под каждой ролью** — живой прогон под каждой ролью на собранной системе:
   видимые разделы, доступные действия, попытка открыть чужой раздел прямой ссылкой; интерфейс
   действительно скрывает недоступное; финансы КП не видны вне задачи роли; контуры сотрудника и
   контрагента не пересекаются.
3. **Площадка и изолированный контур** — место размещения, ответственные (администрирование,
   резервные копии, обновления), исходящий доступ, способ доставки образов, выгрузка логов,
   доступ поддержки, контур передачи данных в ИИ.
4. **Подписка СБ на события** — классы и уровни событий журнала ИБ, адресаты, частота писем.

Требования к серверу (базовые):

| Пункт | Требование |
|---|---|
| ОС | Ubuntu Server 24.04 LTS или Debian 13, x86_64; Docker CE и Docker Compose v2 |
| Сеть | Наружу открыты только 80 и 443 (TCP); административный доступ — по ключу и через VPN; порты СУБД, хранилища, почты и внутренних служб наружу не публикуются |
| Домен и TLS | Публичный адрес (или внутренний DNS контура) и сертификат на домен приложения (и хранилища, если оно отдаётся браузеру по своему домену) |
| Исходящий доступ | HTTPS для обновлений и образов — либо локальное зеркало registry в изолированном контуре |
| Диски | Отдельные тома под БД, файлы, логи контейнеров и резервные копии; ext4, `noatime`; LVM с нераспределённым резервом 10–15 % |
| Ресурсы | См. [demo-deploy.md §1](../08-deploy/demo-deploy.md#1-требования-к-серверу) и [scalability.md §8](scalability.md#8-емкость-одной-реплики-оценка); вариант с локальной моделью ИИ требует GPU и согласуется отдельно |
| Контейнеры | Не от root (UID 10001 в прод-образах), только чтение кода в образе, healthcheck у каждого сервиса |

- **SEC-52.** Исполнитель передаёт Заказчику чек-лист развёртывания по этим четырём шагам и
  протокол проверки доступа под каждой ролью. **S**

## 12. Соответствие законодательству о персональных данных (152-ФЗ, обобщённо)

- **SEC-53.** В системе обрабатываются ПДн: ФИО, телефон, email пользователей и представителей
  контрагентов, ФИО руководителя контрагента. Паспортные и банковские данные не собираются; при
  появлении — заводятся как шифруемые поля. **M**
- **SEC-54.** Базы данных с ПДн граждан РФ должны размещаться на территории РФ (локализация);
  передача ПДн за рубеж (в т.ч. в зарубежный ИИ-шлюз) — трансграничная и требует уведомления
  регулятора; поэтому в ИИ уходят только позиции, цены и условия без ФИО и контактов (SEC-46).
- **SEC-55.** Система поддерживает: журнал действий с ПДн (журнал ИБ), шифрование ПДн при хранении
  (с оговоркой о несертифицированном СКЗИ), разграничение доступа по ролям и объектам, маску
  контактов, подготовку пакета сведений для уведомления регулятора (раздел ИБ).
- **SEC-56.** Согласие на обработку ПДн при саморегистрации контрагента, политика обработки ПДн,
  сроки хранения и порядок удаления по запросу субъекта, требования к классу защищённости ИСПДн и
  к сертификации СКЗИ — определяются Заказчиком (см. открытые вопросы).
